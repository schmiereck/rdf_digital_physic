### 2. Breeder Exploit Gaps

**In `fitness_functions.py`:**

- **Bit conservation only checks initial + final states.** Both `NetDisplacementFitness` and `SubLightFitness` have an `expected_bits = 3` gate that checks the bit count at step 0 and step `max_steps`. A breeder that **creates new particles mid-simulation then annihilates them** before the final step would pass this check.
- **`strict_bit_conservation` exists but is disabled by default.** This is the real breeder prevention — it checks `grid.sum() == expected_bits` at **every single step** in the loop. But since the default is `False`, any code using these fitness classes without explicitly enabling strict mode is vulnerable to breeders.

**In `validate_fitness.py`:**

- No breeder references or checks at all. It only validates that known drifter rules score lower than known glider rules.

### 3. Import/Logic Issues Worth Correcting

**a) `validate_fitness.py` imports from `new_fitness` (line 23):**
```python

```
This imports from `src/new_fitness.py` — a module not shown here. If this is a legacy module that should have been replaced by `fitness_functions.py`, that's a code health issue. Need to check what `new_fitness.py` contains to decide if it's still needed.

**b) `fitness_functions.py` uses two different CoM functions inconsistently:**

- `NetDisplacementFitness.evaluate()` uses the **naive** `center_of_mass` from `evolution` (line 191, 217):
  ```python
  initial_com  = center_of_mass(grid)
  final_com    = center_of_mass(grid)
  ```
- But `SubLightFitness.evaluate()` and the module's own private `_toroidal_center_of_mass()` use a **wrap-aware circular-mean** CoM for toroidal continuity.

The naive `center_of_mass` is discontinuous at toroidal boundaries — a single wrapped cell can jolt the CoM by ~grid_size/n_cells. `NetDisplacementFitness` could benefit from using the toroidal-aware version for its net-displacement calculation too.

**c) Redundant assertion in `__call__`:**
Both fitness classes have this in their `__call__` method:
```python
assert isinstance(result, tuple) and len(result) == 2, ...
```
This is defensive but unnecessary since the tuple is explicitly constructed on the line above. The assertion can be safely removed.
